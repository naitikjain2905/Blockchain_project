
Software Requirements Specification
Anonymous Complaint Box Using Blockchain
Version 1.0 · Prepared following the IEEE 830 structure

1. Introduction
1.1 Purpose
This document specifies the requirements for the Anonymous Complaint Box, a blockchain-based web application where students can submit complaints without revealing their identity, and an authority can review and respond to them. Complaints, once submitted, cannot be edited or deleted by anyone, which builds trust in the system.
1.2 Scope
The system consists of:
A smart contract (Solidity) deployed on the Ethereum Sepolia test network that stores complaints, assigns IDs, and controls status updates.
A web frontend (React) with a student interface and an admin interface.
Wallet-based access through MetaMask, so no name, email or password is collected.
Hosting of the frontend on AWS Amplify or S3.
The system does not include a traditional backend server, a user database, email notifications, or identity verification in version 1.0.

2. Overall Description
2.1 Product Perspective
The product is a standalone, serverless dApp with three core parts: the web frontend, the user's wallet, and the smart contract. There is no central database; the blockchain is the single source of truth.
Student / Admin Browser (React app on AWS)        |  ethers.js + MetaMask wallet        |ComplaintBox smart contract (Sepolia blockchain)
2.2 Product Functions (Summary)
Connect a wallet and detect the correct network
Submit a complaint with a category and description
Receive a unique complaint ID as proof of submission
Track complaint status using the ID
Browse a public list of complaints (optional public view)
Admin: view all complaints, update status and add a response
View statistics: total, pending, resolved
Record every action as a blockchain event for transparency

2.4 Operating Environment
Desktop and mobile browsers with the MetaMask extension or wallet browser
Ethereum Sepolia test network
Frontend hosted on AWS Amplify or S3 with CloudFront
Development: Node.js, Hardhat, Solidity ^0.8.x, React with Vite
2.5 Design and Implementation Constraints
Data written to the blockchain is permanent and public; the system must warn users not to include personal details.
Only one admin address is set at deployment in version 1.0.
Each submission requires a transaction and a small gas fee (free test ETH on Sepolia).
Complaint text length is limited to control gas cost.
The wallet address is visible on-chain, so anonymity depends on users using a fresh wallet.
2.6 Assumptions and Dependencies
Users have a Sepolia wallet funded with test ETH from a faucet.
Sepolia and the RPC provider (Alchemy or Infura) remain available.
The admin keeps the admin wallet's private key secure.
AWS hosting remains available.

4. External Interface Requirements
4.1 User Interface
A responsive single-page application with these screens:
Home: project introduction, Connect Wallet, statistics
Submit Complaint: category, description, privacy warning
Track Complaint: search by complaint ID
All Complaints: filterable public list
Admin Panel: visible only to the admin wallet
General UI requirements: clear loading and error states, readable on screens from 360 px wide, and a persistent notice about the public nature of blockchain data.
4.2 Hardware Interfaces
No special hardware; any device with a modern web browser.
4.3 Software Interfaces
MetaMask (EIP-1193 provider) for account access and signing
ethers.js to read from and write to the contract
JSON-RPC provider (Alchemy or Infura) for Sepolia
Etherscan (Sepolia) for transaction viewing
AWS Amplify or S3/CloudFront for hosting
4.4 Communication Interfaces
HTTPS between browser and hosting; JSON-RPC over HTTPS or WebSocket between wallet/browser and the Ethereum node.

5.5 Contract Security Requirements
SC-1: An onlyAdmin modifier shall restrict status updates.
SC-2: There shall be no function that edits or deletes a complaint's original text.
SC-3: Input length limits shall prevent oversized submissions.
SC-4: The contract shall not hold or transfer funds.
SC-5: (Optional) A cooldown per address shall limit spam submissions.

6. Non-Functional Requirements
6.1 Performance
The frontend shall load within 3 seconds on a normal broadband connection.
Reading complaints shall complete within 2 seconds under normal RPC conditions.
Transaction confirmation may take 12–30 seconds on Sepolia, and the UI shall show progress.
6.2 Security
Private keys shall never be handled by the application.
Deployment keys and API keys shall be kept in .env files excluded from version control.
The contract shall be tested for unauthorised access attempts.
6.3 Privacy and Anonymity
The system shall not collect or store names, emails, phone numbers or IP-based identifiers.
The interface shall explain the limits of pseudonymity and recommend using a fresh wallet.
6.4 Integrity and Transparency
Complaints shall be tamper-proof once recorded.
Every status change shall be publicly verifiable through events and Etherscan.
6.5 Reliability and Availability
The contract is available as long as the Ethereum network is available.
The frontend shall handle rejected or failed transactions gracefully.
6.6 Usability
A first-time user shall be able to submit a complaint in under 2 minutes.
Error messages shall be human-readable.
6.7 Portability and Maintainability
The frontend shall work on current Chrome, Firefox, Brave and Edge and be mobile-responsive.
Code shall be modular, commented, and documented in a README.

7. Use Cases
UC-1: Submit a Complaint
Actor: Student
Precondition: Wallet connected on Sepolia with a small amount of test ETH
Main flow: Student opens Submit page → selects category → writes description → confirms in MetaMask → contract stores complaint → system shows the complaint ID
Alternate flow: Empty or oversized description, or rejected transaction → error shown and nothing stored
UC-2: Track a Complaint
Actor: Student or visitor
Main flow: User enters complaint ID → system reads the contract → shows status and admin response
UC-3: Review and Respond
Actor: Admin
Precondition: Connected wallet is the admin address
Main flow: Admin opens Admin Panel → selects a complaint → chooses new status and writes a response → confirms in MetaMask → status and response are recorded
Alternate flow: A non-admin attempts the action → contract rejects it
UC-4: View Statistics and List
Actor: Anyone
Main flow: User opens Home or All Complaints → system reads contract → shows counts and filtered list

8. Other Requirements
8.1 Testing Requirements
Hardhat tests shall cover: successful submission, ID increments, empty and oversized input rejection, admin-only status updates, rejection of non-admin updates, correct event emission, and the fact that original text cannot be changed. Manual end-to-end testing shall be done on Sepolia with two wallets (student and admin).
8.2 Deployment Requirements
The contract shall be deployed to Sepolia with a Hardhat script, setting the deployer as admin.
The frontend shall be deployed to AWS Amplify (connected to GitHub) or S3 with CloudFront.
